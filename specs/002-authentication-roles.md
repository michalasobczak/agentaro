# 002 — Authentication, roles and TOTP

Status: **implemented** 2026-11-19 (closed by owner: "specs 2 - 4 accept, go" — all proposals accepted). Security findings: spec 005.
Date: 2026-11-19
Depends on: [001](001-initial-structure.md)

## 1. TL;DR

Only people with an account created by an admin can use Agentaro. They sign in with a password, plus a Google Authenticator code (TOTP) — always for admins, for regular users when an admin turns it on. Without outgoing mail, a lost password is recovered through a one-time link generated by an admin; admin passwords can be changed only from the command line. Confirmed by tests of sign-in, roles, TOTP, links and session expiry.

## 2. Abstract

**Current state.** The application is a blank Rails app (spec 001). Every page is public, and it can be reached from the local network.

**Gap.** Agents will act on the owner's behalf using paid subscriptions, so nobody may use the system without signing in, and admin actions must be separated from regular use.

**Rationale.** Rondo E10 (verify identity: secure passwords, 2FA, TOTP mandatory for administrators, no account enumeration) and E11 (least privilege, authorization on every access). ISO 27001 A.5.17 (authentication information, identity verified before a reset) and A.8.5 (secure authentication).

**Decision history (owner, 2026-11-19).**
- Accounts are created only by admins; the first admin is created from the command line.
- TOTP is mandatory for admins; for regular users an admin enables or disables it.
- No outgoing mail. Password recovery: the admin generates a password-change link and hands it over. An admin's own password can be changed only from the command line.
- Sessions are revoked 7 days after sign-in.

## 3. Objective

**Goals**
- G1. Users with a username, a password and a role: `admin` or `user`. *(accepted: username instead of e-mail — there is no mail to verify an address)*
- G2. Sign-in with password; then a 6-digit TOTP code when the account has TOTP. Works with Google Authenticator (RFC 6238, SHA-1, 30 s, 6 digits).
- G3. Sessions stored in the database; each lasts at most **7 days from sign-in** *(accepted: fixed, not sliding)*. Users see and revoke their own sessions; admins revoke any user's sessions.
- G4. Authorization: every page requires a signed-in user; admin pages require the `admin` role.
- G5. Admin area: list, create, deactivate and reactivate users; change role; require or drop TOTP per regular user; reset a user's TOTP; generate a password-change link; revoke sessions.
- G6. Password-change link: one-time, valid for **24 hours**, shown once to the admin. Also used for new accounts — the admin creates a user and hands over the link; nobody else knows the first password.
- G7. Command line (run on the server): `bin/rails agentaro:admin:create`, `agentaro:admin:password`, `agentaro:admin:reset_totp`. Creating an admin enrols TOTP immediately — the terminal shows the QR code.
- G8. Regular users can change their own password (current password required). Admins cannot change any admin password in the web interface.

**Out of scope**
- Outgoing mail of any kind, self-registration, self-service password reset.
- Recovery codes (a lost phone is handled by the admin: TOTP reset + link; for an admin: the command line).
- Roles other than `admin` and `user`; per-resource permissions.
- Single sign-on, passkeys / WebAuthn.

**Success criteria**
- S1. Without a session, every page except sign-in, password-change link and `/up` redirects to sign-in.
- S2. A regular user gets 403 (or redirect with a message) on every admin page.
- S3. An admin cannot finish signing in without a valid TOTP code.
- S4. A session older than 7 days is rejected and deleted.
- S5. A password-change link works once, expires after 24 h, and cannot be generated for an admin.
- S6. A wrong username and a wrong password give the same message and the same response (no account enumeration).

## 5. Functional Domain Changes

**State:** public application → every page behind sign-in; two roles.

**Rules**
- R1. Usernames: 3–32 characters, lowercase letters, digits, `.`, `_`, `-`; unique, case-insensitive.
- R2. Passwords: at least 12 characters, at most 72 bytes (bcrypt limit); no composition rules; rejected if on a bundled list of common passwords or equal to the username (NIST 800-63B).
- R3. Sign-in failures: Rails `rate_limit` per IP (10 attempts / 3 min); after 10 consecutive failures the account is locked for 15 minutes. Same message for unknown user, wrong password, locked or inactive account.
- R4. TOTP: a code is accepted once (replay of the last used time-step is rejected); ±1 time-step of drift allowed. Secrets are stored encrypted. Enrolment shows a QR code and asks for one valid code before it takes effect.
- R5. A regular user with `otp_required` but no secret must enrol TOTP right after the password step; until then the session gives no access.
- R6. Admins always have `otp_required`; it cannot be switched off in the web interface. At least one active admin must exist — the last admin cannot be deactivated or demoted.
- R7. Sessions: new session id on sign-in (no fixation); cookie `httponly`, `SameSite=Lax`, `secure` in production; deleted on sign-out. All of a user's sessions are revoked when the password changes, the role changes, TOTP is reset or the account is deactivated.
- R8. Password-change links store only a digest of the token; using one sets the password, clears lockout, revokes all the user's sessions and marks the link used. Generating a new link invalidates older unused ones.
- R9. Accounts are deactivated, never deleted (history stays consistent for specs 003–004).

**Resilience:** none external (no mail, no network services). Clock drift on the server affects TOTP (±30 s tolerated).

**Data:** new tables in the main SQLite database; migrations reversible.

## 6. Critical Path

Rails authentication generator (trimmed) → users with roles and rules R1–R3 → sessions with 7-day expiry → TOTP enrolment and verification → authorization (admin vs user) → admin user management and password-change links → command-line tasks → tests for S1–S6.

## 8. Expected Outcome

- **Direct effect:** the application is usable only after signing in; admins manage users without mail.
- **Measurable effect:** 0 pages reachable without a session apart from sign-in, link and `/up`.
- **Side effects:** a fresh clone needs one extra step — `bin/rails agentaro:admin:create`. Losing the phone of the only admin requires access to the server.
- **Rollback:** revert the commit and the migrations; no other data exists yet.
